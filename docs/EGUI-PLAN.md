# План UI mbrs на egui: практики, варианты дизайна, порядок работ

Документ отвечает на три вопроса: как правильно строить большое приложение на egui, какие есть варианты
интерфейса для аналога Modbus Poll и в каком порядке это делать. Все правила — с источниками, потому что
половина решений здесь имеет неочевидные последствия для производительности.

Текущее состояние: `mbrs` уже написан на egui/eframe 0.29 (десктопный бинарь `src/main.rs` → `app.rs`, 1 600 строк),
ядро (`modbus.rs`, `formats.rs`, `colors.rs`, `scada.rs`, `store.rs`) вынесено в библиотеку и общее с Tauri-фронтендом.
То есть переписывать на egui нечего — речь о том, чтобы довести его до состояния, в котором не стыдно продавать.

---

## 1. Что говорит практика про egui (и что из этого — наши риски)

**Immediate mode означает, что интерфейс строится заново каждый кадр.** Главное правило — не строить виджеты,
которые не видны, и не делать тяжёлых вычислений внутри `update`
([структура сложного приложения](https://app.studyraid.com/en/read/105424/4737052/structuring-a-complex-egui-application),
[производительность](https://app.studyraid.com/en/read/105424/4737053/performance-considerations-and-optimization)).

| Практика | Как это выглядит в коде | Наш статус |
|---|---|---|
| Состояние отдельно от отрисовки | один `struct MbApp`, никакой логики в замыканиях UI | уже так: `app.rs` + `store.rs`/`modbus.rs` в lib |
| Таблицы виртуализируются | `egui_extras::TableBuilder` + `body.rows(h, n, …)` строит только видимые строки ([док](https://docs.rs/egui_extras/latest/egui_extras/struct.TableBuilder.html)) | сделано вручную: `src/grid.rs::visible_range` + `ScrollArea::show_viewport` (только видимые строки, заголовок вне прокрутки) |
| Никаких аллокаций и `format!` в горячем цикле | кэшировать строки отображения по значению, а не собирать каждый кадр | **не сделано**: в ячейке на каждый кадр идут `format!` + `HashMap`-поиски |
| Стабильные `Id` у повторяющихся виджетов | `ui.push_id(addr, …)` в строках таблицы | **не сделано** — при виртуализации это станет обязательным |
| Панели, а не «одно полотно» | `egui_dock` (вкладки-доки, отрыв в отдельное окно), `egui_tiles` как модель дерева ([egui_dock](https://docs.rs/egui_dock/latest/egui_dock/), [egui_docking](https://github.com/Latias94/egui_docking)) | сейчас одиночные вкладки `View::{Grid,Scada,Chart,…}` |
| Графики — отдельным крейтом | `egui_plot` | свой `draw_chart()` |
| UI-тесты | `egui_kittest`: `Harness::new_ui`, клики по AccessKit-узлам, снапшоты (для снапшотов нужен `wgpu`) ([egui_kittest](https://docs.rs/egui_kittest/latest/egui_kittest/)) | нет; логика тестируется отдельно (`cargo test`, 16 тестов) |
| Сохранение состояния окна/панелей | `eframe::Storage` (или свой JSON, как сейчас) | свой `*.mbw` есть, геометрия окна не сохраняется |

Практический вывод: следующая узкая по объёму и большая по эффекту работа — **не** красивый редизайн, а
(а) кэш отображаемых строк, (б) стабильные `Id`, (в) перенос сетки на `TableBuilder` с колонками-ручками,
(г) `egui_dock` для панелей. После этого интерфейс можно свободно перекраивать без страха за FPS.

## 2. Три варианта дизайна (и что выбрать)

Modbus Poll — это **MDI**: каждое окно = одно определение опроса (slave ID, функция, диапазон, формат), окон
может быть много одновременно, в ячейках можно писать произвольный текст (Alias), F1 даёт справку по любому
диалогу ([quick start](http://modbustools.com/quickstart.html), [manual](https://modbustools.com/mbpoll-user-manual.html)).
Это не «таблица», это набор рабочих листов — и именно поэтому инженеры её не бросают.

| Вариант | Как выглядит | Плюсы | Минусы |
|---|---|---|---|
| **A. Табы (сейчас)** | одна сетка + переключатели Grid/Scada/Chart/Traffic/Scan/Test | просто, предсказуемо | нельзя смотреть два диапазона/два slave рядом — главный сценарий пусконаладки |
| **B. Доки (рекомендую)** | `egui_dock`: вкладки-таблицы, каждая панель — своё определение опроса; любую можно оторвать в отдельное окно | паритет с MDI по смыслу, но без MFC-окон; один код на панель; работает на Linux/macOS | нужен крейт и аккуратная модель состояния панелей |
| **C. Дашборд-первым** | на старте — плитки SCADA, таблицы по кнопке | лучший вид «для начальника», меньше когнитивной нагрузки | пусконаладчику нужны цифры, а не плитки; нельзя как единственный режим |

**Решение: B + C как равноправные режимы.** Стартовый экран — док-раскладка с панелью таблиц (по умолчанию
одна) и необязательной панелью плиток; вкладка «Дашборд» открывается с той же раскладкой, но на весь экран.
«Test Center» (посылка произвольного кадра) и «Traffic» остаются док-панелями, чтобы их держать рядом с сеткой —
именно так их держат в Modbus Poll.

Дизайн-детали, которые стоит заимствовать у оригинала (проверенные годами у инженеров):
- Alias-ячейка: любой текст в строке рядом с адресом (комментарий, тег, ссылка на схему);
- F1 в каждом диалоге, клавиши `F3/F4/F5`, `Alt+F5…F8` — уже реализовано;
- подсветка цвета значения (наш цветовой движок здесь сильнее оригинала);
- «Display → 28 форматов» + масштабирование (у нас есть);
- объединённые графики на несколько регистров (у нас один strip chart — в бэклог);
- счётчики ошибок/таймаутов по каждой группе (у нас есть).

## 3. Порядок работ (каждая позиция — задача, а не пожелание)

1. **Кэш строк отображения** (`formats.rs` → `RenderCache` по `(CellKey, ValueFormat, Scale)`): убрать `format!`
   из кадра. Проверка: бенчмарк-тест `cargo test --release format_cache` — 10 000 обращений дешевле X мкс.
2. **`ui.push_id(addr)` в строках** + регресс-тест, что выделение мыши не «прилипает» к чужой строке после скролла.
3. **Сетка на `egui_extras::TableBuilder`** с колонками: `addr`, `raw`, `value`, биты (опционально), Alias.
   Ресайз колонок, «залипающая» шапка, выделение строки целиком — то, что ручная отрисовка не даёт.
4. **`egui_dock`**: каждая панель = определение опроса; раскладка сохраняется в `*.mbw` (поле `layout`).
5. **Симулятор слейва** и «Test Center» как полноценный сценарий (Modbus Poll продаёт именно пару master+slave).
6. **`egui_plot`** вместо своего графика: комбинированные кривые, курсор, экспорт.
7. **`egui_kittest`** для UI-тестов: снапшот главного окна + клик по ячейке меняет выделение (в CI, без GPU —
   только AccessKit-часть, снапшоты отдельной джобой с `wgpu`).
8. **Мелочи, которые решают**: сохранение геометрии окна, тёмная/светлая тема, шрифт под инженерные нужды,
   копирование значений в буфер, экспорт CSV из контекстного меню.

## 4. Чего делать не надо

- **Не переписывать ядро под UI.** `modbus.rs`/`formats.rs`/`colors.rs` UI-агностичны — это главный актив проекта
  (общий с Tauri-фронтендом), и он уже покрыт тестами.
- **Не тащить `wgpu`/`egui_plot` ради красоты.** Сначала кэш и виртуализация, потом визуал: обратный порядок
  даёт красивый интерфейс, который тормозит на 500 регистрах.
- **Не делать плитки единственным режимом.** Пусконаладка идёт по числам; плитки — для наблюдения.
- **Не превращать каждую настройку в диалог.** Modbus Poll выигрывает плотностью: всё видно в одной строке.

## 5. Что уже сделано в этом коммите

- `src/grid.rs`: чистая функция `visible_range(total, row_pitch, viewport_h, scroll_y, overscan)` + 5 тестов
  (границы, скролл за конец, деградировавшие входы, «строим десятки строк, а не десятки тысяч»).
- `app.rs::draw_grid`: шапка вынесена из области прокрутки (не уезжает при скролле), строки рисуются через
  `ScrollArea::show_viewport` + `allocate_ui_at_rect` только для видимого диапазона.
- `examples/gen_demo.rs` + `examples/demo.mbw`: демо-проект воспроизводим, а тест `demo_workspace_parses`
  до этого не компилировался на свежем клоне (`include_str!` на отсутствующий файл) — `cargo test` теперь
  проходит целиком: 16 тестов.
